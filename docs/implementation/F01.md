# F01 — execution-bound verification

Status: locally verified, 2026-10-21. Release/native qualification and real-provider
measurements remain part of the final integration gates.

## Behavior

- The existing `ur spec verify` and kernel verifier share
  `runExecutionBoundVerification`. The model still chooses its commands. Existing
  permission modes, approvals, tool access, and verifier opt-outs are unchanged.
- Verification children use the existing SDK stream to collect runtime-emitted
  shell execution IDs, exact commands, exit codes, interruption state, and source
  fingerprints. Proof headings must reference those executions by exact command
  or `execution:<tool_use_id>`. Prose alone cannot establish PASS.
- Failed, incomplete/background, foreign-run, foreign-workspace, mismatched-command,
  or stale-state executions cannot supply successful proofs. Runner/SDK errors
  override claimed PASS. The final standalone verdict marker is authoritative.
- Source fingerprints include Git-visible tracked/untracked file contents,
  executable modes, symlinks, HEAD/index flags, specification inputs, and verify
  policy. Git-independent workspaces use a bounded filesystem scan. Generated
  UR runtime state and verification reports are excluded.
- Shell/Python changes observed during a turn feed the existing after-edit
  verification path, including partial writes from failed commands. Successful
  read-only shell calls no longer count as evidence of file mutation.
- Verification records use schema 2, with source digest, run ID, proof-to-execution
  bindings and command digests. Legacy schema-1 PASS migrates to explicitly
  unverifiable PARTIAL. Loading a result rechecks current source state; stale or
  incomplete PASS evidence becomes PARTIAL. Both direct and kernel spec paths
  persist through the same helper. `loadVerificationRecord` and
  `listVerificationRecords` are now asynchronous.
- Headless runner options additionally support session ID/resume, dollar budget,
  cancellation and child-PID publication through `onSpawn`. Returned cost, usage, turns and session ID come from actual
  SDK result fields; unknown values are omitted rather than guessed as zero.

## Limits and follow-up documentation

- No model/provider was called by these tests. Reported cost/session fixtures
  validate metadata plumbing, not real-provider billing or benchmark quality.
- Command relevance and semantic feature correctness still require the verifier's
  judgment and project assertions. Execution binding proves what ran against
  which captured source state; it does not turn an arbitrary successful command
  into a complete correctness oracle.
- Snapshots cover the declared workspace source scope, not external services or
  arbitrary ignored/outside files. They are bounded at 20,000 files/128 MiB;
  unavailable snapshots cannot establish PASS. Local records are not signed
  remote attestations. Turn-wide file observation is not OS-level causal auditing
  of concurrent writers.
- The executable integration fixtures are POSIX-only and explicitly skip Windows.
  PowerShell exit metadata is wired, and its ledger attribution is covered; an
  actual Windows/PowerShell runtime qualification is still required before
  claiming that platform support.
- Update technical/09 and technical/10 for execution-bound spec/kernel proofs,
  schema-2 migration, asynchronous record loading, and headless metadata. Update
  technical/12 for observed shell mutations and the unchanged permission/sandbox
  boundary. Root owns final cross-cutting documentation/release claims.
