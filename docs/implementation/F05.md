# F05 — persistent goal controller

Status: locally verified (2026-10-21). External publication remains pending. The deterministic failure fixtures
and bounded live-model observation below measure different behavior.

## Canonical behavior

`ur goal resume` now advances a goal even without a linked workflow. The model
chooses direct work, a saved workflow, another iteration/replan, outcome
verification, or a concrete blocker. The controller defines a result protocol,
not a fixed task plan or tool strategy. Workflow completion is recorded as
progress and returned to the model; it never automatically marks an objective
achieved. The existing user permission and model choices remain in effect.

`goal add` accepts repeated `--criterion` values. When omitted, the objective is
the criterion. Existing goal files migrate on read without rewriting them:
historical done states are labeled manual, never retroactively verified.
Explicit `goal done` remains user attestation and is displayed as manual.

A separate criterion assessment must support every criterion before automatic
done. The model chooses relevant checks. Successful command receipt IDs must
match the current verification nonce, cwd, successful uninterrupted execution
and exact source fingerprint. Current file observations require an exact
supporting excerpt; the controller reads the file itself and records its hash.
Paths escaping the workspace, fabricated/missing/failed/stale receipts,
unsupported excerpts, runner errors and source changes cannot authorize done.
This deliberately does not impose compile/test/lint categories on research or
documentation goals. It validates evidence provenance, not a mathematical proof
that arbitrary natural-language criteria are semantically true. Browser-only
semantic claims currently need a persisted artifact or command receipt.

## Persistence and budgets

Schema-2 goal files atomically persist criteria, progress, model feedback,
blockers, outcome assessments, controller ownership and in-flight session IDs.
The existing `goal pause` cancels the active child through its actual abort
signal. A killed controller resumes the same saved session ID with explicit
unknown-outcome/reconciliation context; it does not script old tool commands.
A surviving known child prevents a duplicate launch. A production launch killed
before child-PID persistence requires process inspection rather than guessing.

Calls, actual SDK turns, reported cost, active elapsed time and unknown usage
are accumulated across resumes. Controlled workflow steps and independent
verification calls share that ledger and receive the remaining turn/cost/time
limits. Increasing an explicit budget never resets consumed usage. All caps are opt-in; absent a user-specified cap, useful progress has no fixed
invocation ceiling. Two repeated responses against the same observed source
state persist a loop-stall blocker instead of spending indefinitely on replay. `--max-turns` is now an
aggregate goal budget, not a fresh allowance per workflow step. Unknown paid
usage is reported as unknown, not zero; when a monetary/turn cap cannot be
established the controller stops with a persistent budget blocker. Resolve
unknown provider accounting before editing that persisted accounting/cap.

Budget scope is controller-dispatched UR invocations and SDK-reported usage
(including work attributed by that invocation). It cannot establish costs of
arbitrary out-of-band programs/services launched by a shell tool. The model is
instructed to request the controlled workflow path rather than recursively
launch commands outside the ledger. This is not an OS billing sandbox. Active
elapsed time is periodically checkpointed; a hard crash can lose the final
heartbeat interval, and provider spending after a lost process remains unknown.

A changed objective/criteria/linked strategy cannot silently reuse prior goal
execution state. Create an explicitly new goal after reviewing the previous
work. Concurrent controllers, notes and status changes use locked atomic state;
active owner fencing prevents stale updates. Dry run leaves state, usage and
outcome unchanged and does not claim execution evidence.

## Files and public flags

- `src/services/agents/goals.ts`: durable schema/accounting/status/migration.
- `src/services/agents/goalController.ts`: model-directed loop, aggregate budget,
  workflow continuation, cancellation and criterion evidence assessment.
- `src/commands/goal/{goal,index}.ts`: canonical command integration/help.
- `src/main.tsx`: parent-owned forwarding for repeatable `--criterion`,
  `--max-calls`, aggregate `--max-turns`, `--max-budget-usd`,
  `--max-duration-ms`, `--model` and `--skip-permissions`.
- `test/goalController.test.ts`: real killed controller/file effect and pause,
  budget restart, workflow false-completion, valid current observations and
  fabricated/stale/failed evidence cases. No parent module mocks or paid calls.

## Documentation recommendations

Update technical/09 and technical/14 plus goal command help/reference to describe
model-directed resume without a workflow, explicit criteria, aggregate budget
semantics, manual versus verified outcomes, persistent blockers, unknown usage
and resumable interruption. Remove the former claim that workflow completion
means the objective is done. Describe filesystem/command evidence scope honestly
and keep real-provider long-horizon success rates separate from these fixtures.

## Native live-model observation

The actual macOS ARM64 native candidate ran a synthetic slug-normalization goal
through MiniMax on Ollama Cloud with no Bun on the child PATH. The first run
correctly stopped at its explicit aggregate turn budget without claiming success.
A resume with a larger explicit budget preserved all prior work/consumption,
reconciled earlier mistaken model test expectations and completed both criteria
with current file observations and execution evidence. Total across both runs:
4 calls, 42 SDK-reported turns, 199,649 ms active time; all four calls had unknown
pricing. Outcome: verified. This one synthetic goal demonstrates actual native
resume/evidence behavior; it is not a long-horizon reliability score. The logs
remain `/private/tmp/ur-frontier-live-goal-native.log` and
`/private/tmp/ur-frontier-goal-resume.log`.
